Database Normalization Process

Transforming Unstructured Data into a Normalized Database Schema

What is Database Normalization?

Database normalization is the process of organizing data in a database to reduce redundancy and improve data integrity. It involves dividing large tables into smaller, related tables and defining relationships between them. The goal is to eliminate data anomalies and ensure that each piece of data is stored in only one place.

Normalization Objectives:

  • Eliminate redundant data - Store each piece of data in only one place
  • Ensure data dependencies - Make relationships between data clear and logical
  • Reduce update anomalies - Changes should be made in only one place
  • Maintain data integrity - Ensure data accuracy and consistency

Step 1: Unnormalized Form (UNF)

The starting point is a single large table containing all information. This represents how data might be stored in a spreadsheet or simple file-based system.

Problems with UNF:

  • Multivalued attributes (CustomerPhones, FoodItems)
  • Data redundancy across rows
  • Insertion, deletion, and update anomalies
  • No clear relationships between data elements

Unnormalized Order Table:

OrderID CustomerName CustomerPhones FoodItems Restaurant Rider PaymentModes

O002 John Smith 555-1234, 555-5678 Burger, Fries McDonald's Sarah Wilson Debit Card

Issues Identified:
  • CustomerName "John Smith" is repeated
  • CustomerPhones contains multiple values in one cell
  • FoodItems has multiple items in one field
  • PaymentModes has multiple payment options

Step 2: First Normal Form (1NF)

A table is in 1NF if it contains only atomic (indivisible) values and no repeating groups. This eliminates multivalued attributes.

1NF Rules:

  • Each cell must contain a single value
  • No repeating groups or arrays
  • Each column must have a unique name
  • The order of rows and columns is irrelevant

Step 3: Second Normal Form (2NF)

A table is in 2NF if it is in 1NF and all non-key attributes are fully functionally dependent on the primary key (no partial dependencies).

2NF Rules:

  • Must be in 1NF
  • No partial dependencies on composite primary keys
  • All non-key attributes must depend on the entire primary key

Identifying Partial Dependencies:

CustomerName → PhoneNumber

This shows that PhoneNumber depends only on CustomerName, not on the full key.

  • Customer data is no longer duplicated in orders
  • Customer information changes affect only one table

Step 4: Third Normal Form (3NF)

A table is in 3NF if it is in 2NF and there are no transitive dependencies. Non-key attributes must not depend on other non-key attributes.

3NF Rules:

  • Must be in 2NF
  • No transitive dependencies (A → B → C)
  • All non-key attributes depend directly on the primary key

Identifying Transitive Dependencies:

Restaurant → RestaurantLocation
Rider → RiderContact

These create transitive dependencies through the Orders table.

Step 5: Fourth and Fifth Normal Forms (4NF & 5NF)

4NF deals with multi-valued dependencies, while 5NF handles join dependencies. For most practical purposes, 3NF is sufficient, but we'll briefly cover higher normal forms.

4NF & 5NF Overview:

  • 4NF: No multi-valued dependencies
  • 5NF: No join dependencies (also called PJNF)
  • Most business databases are normalized to 3NF
  • Higher normal forms are rarely needed in practice
Conclusion: Our Food Delivery database is fully normalized to 3NF, which eliminates all practical data anomalies while maintaining query performance. Higher normal forms (4NF/5NF) are not typically required for this application domain.
